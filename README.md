# 门店积分到期与退货逆向冲销

给连锁零售会员运营专员使用。消费先用最早到期批次；退款按原消费分配逆向恢复，已过期部分不得复活。

七个业务模块：事件采信、权益规则、积分归批、消费到期、退货回拨、余额对账、期末归档。

```sh
docker compose up --build -d
docker compose exec -T app pytest -q
```

访问 http://localhost:18242 。启动直接载入现场脏批。切换干净样例、旧编码样例和新旧合并样例可对照核验。会员00001两批积分100和80，消费120后退款30，其中20恢复、10已过期不恢复；再消费50后余额30。整批发放1580、余额1010、消费730、退款170、到期10，守恒可复核。

新旧合并样例（`mixed`）在旧账之上叠加新门店三笔：发放250、消费170、退款60，合计发放1830、可用1150、消费900、退款230、到期10。来源账按旧门店/新门店/合计三行分别闭合。

各模块页面对应 `/<模块英文名>`，各模块执行入口为 `POST /api/<模块英文名>`，不传参即可独立演示。完整运行 `POST /api/runs` 支持 `dataset`（dirty/clean/legacy/mixed）、`csv_text` 与 `overrides` 参数。批次历史 `GET /api/runs`，详情 `GET /api/runs/{run_id}`。

同输入与规则版本生成相同批号，只保留一条批次。复核入口 `POST /api/runs/{run_id}/review` 提交当前 `revision`，陈旧提交409。归档包只有一个下载入口 `GET /api/export/{run_id}`，含证据、合并账与退货依据。原始隔离在页面同屏显示。

## 来源合并与发布

旧门店只有九列；新门店可追加 `source,channel,reason` 三列。旧格式整批按旧门店采信并补 `legacy_compat`，不补造渠道和原因；合并格式可逐行指定来源。两路重复投递的同一事件只记一次，被并行的旧行进入隔离留证，重跑同一批积分不会重复记账。

新门店每笔退货必须能追到兑换渠道、退货原因和同会员原消费，缺失即阻断发布但不改记账算术。

发布 `POST /api/runs/{run_id}/publish`：对账闸门四项全通过才落账，否则409 `RELEASE_BLOCKED`；中断回滚保留旧版；同批重发幂等；同日不同批次形成递增发布版本，旧版 `superseded`。查询 `GET /api/releases/{day}` 和 `GET /api/releases/{day}/active`。

页面显示来源账、退货依据、可用余额和发布状态，归档页提供发布按钮与发布历史。

SQLite使用命名卷，容器重启后保留历史。要重建演示可在Compose中改用新的卷名称，保留旧卷。

源码在 `app/`，样例在 `sample_data/`，测试在 `tests/`；定义见 `docs/DATA-DICTIONARY.md`，模块和边界测试对应关系见 `docs/DEPTH.md`。输入上限2MB，属于离线复核工具。

采信页支持上传或粘贴CSV。完整源字节与参数随批次持久化，跨页通过run_id读取同一结果。`POST /api/runs/{run_id}/rerun` 读取该批不可变输入快照重新计算，规则未变时批号不变。切换另一示例则创建或复用另一批次。
